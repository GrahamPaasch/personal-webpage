1The objection

"BGP is really only for network borders."
— isaacyonemoto, Discord, 10/12

That was the rule in the 1990s: an IGP (OSPF, IS-IS) inside your network, BGP at the edge to talk to other networks. It's a reasonable rule. It's also not what the biggest networks on earth do inside their AI data centers. Today we find out why, with real numbers from a real lab.

2BGP is an app, not an IGP

eBGP: an application

Rides a normal TCP session on port 179, like a web or database connection. Handshake, then messages: OPEN, KEEPALIVE, UPDATE.

Talks only to its direct neighbors.

Ships answers: "I can reach 172.16.1.0/24, here's the AS path." Only best paths, per prefix.

When something changes, it sends a per-prefix diff. Nobody recomputes the network.

OSPF / IS-IS: a link-state IGP

Its own IP protocol (OSPF = IP protocol 89, multicast to 224.0.0.5). No TCP; it built its own reliability.

Floods every router's link description (LSAs) to every router in the area.

Ships the whole map. Every router holds an identical copy.

When any link changes, every router re-runs SPF (Dijkstra) over the entire map.

The one-liner: OSPF makes every router redraw the whole map. BGP just passes a note about the prefixes that changed.

Neither is "better" in the abstract. Flooding the map is great when the network is small and you want every router to know everything. It gets expensive when there are thousands of routers and links flap all day.

3Why hyperscalers run eBGP inside AI fabrics

RFC 7938, "Use of BGP for Routing in Large-Scale Data Centers" (2016, written from Microsoft's experience), lays out the design we built in episode 1: a Clos (spine-leaf) fabric where every switch is its own BGP speaker and eBGP is the only routing protocol. Their reasons, in plain words:

  • Failures stay local. A flap changes a few prefixes on a few sessions. In a link-state protocol, every flap is news to every router in the area, and every router recomputes.
  • One protocol, simple state. No areas, no DR/BDR elections, no LSDB to keep in sync. Each switch only knows what its neighbors told it.
  • Policy is built in. Drain a switch for maintenance, steer one prefix, filter a route: that's a route-map on one session. Link-state can only change link costs, which floods everywhere.
  • Mature, boring code. Every vendor's BGP is battle-tested at internet scale, and the same skills cover the border and the fabric.

Why this matters more for AI: GPU training fabrics are huge (tens of thousands of links), traffic is synchronized (one slow path stalls the whole job), and optics fail often. You want each flap to touch as little as possible. That's the eBGP property we're about to measure.

4Fair answer: where OSPF and IS-IS still win

The objection isn't silly. Link-state protocols still have real strengths:

  • Small and medium networks. A campus or a branch with 20 routers: OSPF is zero-touch, fast, and well understood. The flooding cost is tiny.
  • Every router sees the whole map. That enables things BGP can't do on its own: precomputed backup paths (LFA / TI-LFA), and segment routing / traffic engineering that needs the full topology.
  • Service-provider cores. Most ISP backbones run IS-IS underneath for loopback reachability and fast reroute, with BGP on top carrying customer and internet routes. That's the "BGP at the border" picture, and it's still right there.
  • Convergence isn't automatically better with BGP. With BFD and tuned timers both converge in well under a second. The win is the blast radius of each change, not raw speed.

So the honest version: "BGP only at the border" was a design choice for networks where an IGP's full-map view was cheap and useful. In a giant Clos fabric the full map stops being cheap, and the per-neighbor, per-prefix model wins. Hyperscalers didn't break the rule; the size of the network did.

5The twin topology

Two labs, built side by side from the same FRR 10.5.5 image (GNS3 projects in the video; two containerlab topologies in the free kit). Same node names, same 9 cables, same loopbacks and host subnets as episode 1. Fair timers on both: 3 s hello/keepalive, 9 s dead/hold. The only difference is the routing protocol. Both twins are unnumbered: BGP peers over IPv6 link-local and carries IPv4 routes with an IPv6 next hop (RFC 8950); the OSPF twin is OSPFv2, the IPv4 version (OSPFv3 is the IPv6 one), with every fabric link borrowing the loopback /32. 6Configs side by side (leaf1)

Left: the episode 1 eBGP config, unchanged. Right: the OSPF twin. Both are the real files running in the lab, and both are unnumbered: no IPv4 subnets on fabric links. The only difference is the routing protocol.

eBGP twin — leaf1

frr defaults datacenter
Datacenter profile: keepalive 3 s, hold 9 s, fast advertisement.
interface lo ip address 10.0.1.1/32 interface eth2 ip address 172.16.1.1/24
Loopback and host LAN. No IPv4 on the fabric links at all.
router bgp 65101 bgp router-id 10.0.1.1 bgp bestpath as-path multipath-relax
Own AS per leaf. Multipath-relax lets two paths via different spines both be used (ECMP).
neighbor FABRIC peer-group neighbor FABRIC remote-as external neighbor eth0 interface peer-group FABRIC neighbor eth1 interface peer-group FABRIC
The app part: open a TCP 179 session to whoever is on eth0 and eth1. No neighbor IPs typed; it finds them over IPv6 link-local.
address-family ipv4 unicast network 10.0.1.1/32 network 172.16.1.0/24
The answers leaf1 publishes: its two prefixes. That's all a flap of leaf1's link can ever change.

OSPF twin — leaf1

frr defaults datacenter
Same profile, same image.
interface lo ip address 10.0.1.1/32 ip ospf area 0
Loopback advertised into area 0.
interface eth0 description to-spine1 ip address 10.0.1.1/32 ip ospf network point-to-point ip ospf area 0 ip ospf hello-interval 3 ip ospf dead-interval 9 interface eth1 description to-spine2 ip address 10.0.1.1/32 (same four ip ospf lines)
Unnumbered too: each fabric link borrows the loopback /32, so addressing matches the BGP twin. Point-to-point is required for that (and skips DR election). Hello 3 / dead 9 matches BGP's 3 / 9, so both notice the failure at the same time. Routes show onlink: that's correct.
interface eth2 ip address 172.16.1.1/24 ip ospf area 0 ip ospf passive
Host LAN, advertised but passive (no hellos to h1).
router ospf ospf router-id 10.0.1.1
No list of prefixes to publish, no neighbors to name. OSPF describes links, and everyone builds the map.

Spines: BGP spine = router bgp 65000 + neighbor eth0/eth1/eth2 interface peer-group FABRIC + its loopback. OSPF spine = the same eth0 block on eth0, eth1, eth2 (borrowing 10.0.0.N/32) + router ospf. Timers 3 / 9 everywhere.

7Run it yourself (~10 min)

The free kit builds both twins with containerlab on any Linux box with Docker. Everything below is the kit's real commands; the video does the same in GNS3.

  1. Build both twins. One command; it waits until both are healthy (about a minute on our server). 
    $ sudo ./lab.sh up
[BGP twin]
  PASS Established: 12/12  spine1=3 spine2=3 leaf1=2 leaf2=2 leaf3=2
  PASS ECMP leaf1: 172.16.2.0/24=2 172.16.3.0/24=2 10.0.1.2/32=2 10.0.1.3/32=2
  ...
[OSPF twin]
  PASS Full: 12/12  spine1=3 spine2=3 leaf1=2 leaf2=2 leaf3=2
  ...
ALL CHECKS PASSED
  2. OSPF holds the map. OSPF twin, leaf1 (docker exec -it clab-ospf-leaf1 vtysh): 
    leaf1# show ip ospf neighbor          # 2 Full
leaf1# show ip route 172.16.3.0/24    # via 10.0.0.1 eth0 onlink + 10.0.0.2 eth1 onlink
    Then on leaf3 and spine1: show ip ospf database. Same 5 Router LSAs on both. Every router carries the whole map.
  3. BGP holds answers. BGP twin, leaf1 (docker exec -it clab-bgp-leaf1 vtysh): 
    leaf1# show bgp summary               # spine1(eth0), spine2(eth1): 5 PfxRcd, 8 PfxSnt
leaf1# show ip route 172.16.3.0/24    # 2 next hops, fe80:: via eth0 + eth1
    BGP carries answers, not the map.
  4. Predict, then flap. Say out loud which routers you think will react. Then: 
    $ sudo ./lab.sh flap
    It waits for the counters to go quiet, snapshots both twins, starts 10-per-second pings, breaks link 2 (leaf1 eth1 ↔ spine2 eth0) in both twins at the same moment for 20 s, repairs it, waits 20 s, and prints the per-router change. Read spf_runs first. Section 8 has the numbers to compare.
  5. Look at the wire. Capture a BGP session coming up, and OSPF's hellos (section 9).
  6. Tear down when you're done: sudo ./lab.sh down.

How the kit breaks the link: 100% packet loss on both ends with containerlab tools netem, while both interfaces stay up, the same as GNS3's Suspend link in the video. Neither protocol gets a "link down" hint, so both find out by their timers (9 s). ip link set down would be a different, faster test. Break or repair it by hand with sudo ./lab.sh link suspend / resume.

Gotcha from the live build: after the OSPF twin was switched in place from /31s to unnumbered, it showed 12/12 Full but every ping failed: the spines still held the leaves' old /31 addresses as neighbor addresses (FRR doesn't refresh a Full neighbor's address). Fix: clear ip ospf neighbor on both spines. The kit builds fresh, so you won't hit it, but the lesson stands: control plane "perfect" doesn't mean the data plane works. Always ping. (sudo ./lab.sh check does.)

Look at spine1. It isn't on the broken link. In OSPF it still received 9 LSAs and re-ran SPF 3 times. In BGP it sent nothing and changed no routes. Same result from the kit. On containerlab, sudo ./lab.sh flap on a freshly built lab printed the on-camera deltas: OSPF spf_runs +3/+4/+4/+4/+4 (19), lsa_updates +4 on every router; BGP updates_rcvd +2/+6/+5/+2/+2, updates_sent 0/+9/+8/0/0, spine1 sent 0. Your run may differ slightly, and the absolute counters will differ; only the bracketed changes matter.

How to read it: lsa_updates +4 on every router = every router stored the same 4 new versions of the map. rib_routes is a route count, so it's +0 after recovery in both twins; it doesn't mean "untouched". Who actually rewrote routes ("routes changed" above) came from kernel ip monitor route on each router during the flap. Absolute counters depend on how long the lab has been up: always snap, then diff (lab.sh flap does).

The kit's lab.sh flap prints the same loss table for h1→h2 and h1→h3 in both twins. Our kit runs on containerlab: OSPF 68–72 lost, BGP 79–81 lost (the flows that hashed onto link 2). Loss depends on where in the 3-second hello/keepalive cycle the break lands, so expect anything from about 30 to 90 in either protocol.

Say it plainly: BGP did not converge faster. Both lost about 6–9 seconds of traffic (60–86 pings at 10 per second), because both wait for the same 9 s dead/hold timer: hello 3 / dead 9 in OSPF, keepalive 3 / hold 9 in BGP. On leaf1, spine2, leaf2 and leaf3 the forwarding changes were the same in both twins. BGP's win here is blast radius and CPU: no SPF anywhere, no map flooded to everyone, and a router off the path (spine1) doing nothing. Speed comes from BFD, in either protocol (episode 1).

9Wireshark: BGP is just TCP port 179

In the video we captured inside leaf1 and opened the files in Wireshark. With the kit, capture from the host: containerlab registers each container's network namespace under its name, so the host's tcpdump can listen on leaf1's eth0 directly.

$ sudo ip netns exec clab-bgp-leaf1 timeout 15 tcpdump -i eth0 -U -w bgp.pcap 'tcp port 179' &
$ sleep 2; sudo docker exec clab-bgp-leaf1 vtysh -c 'clear bgp eth0'   # fresh SYN, OPEN, UPDATEs
$ sudo ip netns exec clab-ospf-leaf1 timeout 15 tcpdump -i eth0 -U -w ospf.pcap 'ip proto 89'
$ wireshark bgp.pcap ospf.pcap     # or tshark -r bgp.pcap

bgp.pcap

Old session: NOTIFICATION + FIN. Then SYN / SYN-ACK to port 179 over IPv6 link-local, 4 OPEN (both sides dial; one connection wins), 11 UPDATE, KEEPALIVEs. Filter bgp.type == 2; an UPDATE carries 172.16.x.0/24 with AS path like 65000 65103. A socket, a handshake, messages. That's an app. live lab output

ospf.pcap

No TCP. 9 packets in 15 s, all OSPFv2 Hello from 10.0.x.x to 224.0.0.5, IP protocol 89. In steady state there's no LS Update at all; during a flap OSPF uses its own LS Update + LS Ack reliability because it isn't riding a transport. Plumbing, not an app. live lab output

clear bgp eth0 drops that one session for about a second; leaf1 still has eth1, so h1 keeps working. Don't run it during a flap count.

10Exercises

1. Where does the news go?

Each answer can be reproduced with the kit: sudo sh solutions/exerciseN/run.sh applies it to both twins, prints the counter diff and undoes it. Try it by hand first.

In the OSPF twin, shut leaf3's host port (interface eth2 / shutdown). Which routers re-run SPF? Do the same in the BGP twin: which routers' RIBs change, and did anyone recompute?

Answer

OSPF: all 5. leaf3's Router LSA changes and floods area-wide; spf_runs goes +1 everywhere.

BGP: 172.16.3.0/24 is withdrawn from every router's RIB (they all needed that prefix), but nobody ran SPF. 12 UPDATEs in total, a withdraw per session. Same reach, far less work per router. On camera:

2. Scale-out cost

Add a new loopback prefix 10.99.0.3/32 on leaf3 (OSPF: add it on lo, already in area 0; BGP: also network 10.99.0.3/32). Compare the counter diffs (sudo python3 scripts/count.py snap both, change, diff both). What would adding a whole leaf4 cost each protocol?

Answer

OSPF: leaf3 re-originates its Router LSA, every copy of the map gets updated (lsa_updates +1 on all 5), and every router runs SPF (+1 on all 5) for one new /32. BGP: one UPDATE per session (12 in total), +1 prefix everywhere, no recompute. Measured on camera, and the same deltas from the kit. Both twins end up with 2 ECMP next hops to 10.99.0.3/32.

A real leaf4 in OSPF adds a new LSA and changes both spines' LSAs, on every router. In BGP it's one neighbor eth3 interface peer-group FABRIC line per spine (episode 1, exercise 1).

3. Policy is the app feature

In the BGP twin, make spine2 stop carrying traffic for leaf1 only, without touching any link. Can you do the same in OSPF without making other routers re-run SPF?

Answer

BGP: a route-map on spine2 that prepends (or denies) 172.16.1.0/24 outbound, scoped by a prefix-list (episode 1's DRAIN pattern), plus a prepend-everything route-map towards leaf1 so leaf1 stops sending via spine2 too. No SPF anywhere, and spine1 sends nothing. spine2 re-sends its table to the three leaves when the outbound policy changes (21 UPDATEs in our kit run), but that's per prefix, per neighbor, and nobody else recomputes anything.

OSPF: the only knob is link cost (ip ospf cost 1000 on spine2 eth0). That changes a Router LSA, floods everywhere, and every router re-runs SPF: with the cost raised on both ends of link 2, the kit counted +2 SPF runs on all 5 routers (10 total). There's no per-prefix, per-neighbor policy in the protocol; a cost moves everything that crosses the link. Full config in solutions/exercise3/.

11Recap & the kit

  • BGP is an application: a TCP session on port 179, neighbor to neighbor, carrying best paths per prefix.
  • OSPF / IS-IS flood the whole map to every router and every router re-runs SPF on every change.
  • We flapped one link in identical twins: OSPF re-ran SPF on all 5 routers (19 runs, +4 LSA updates on every router); BGP ran SPF nowhere (17 small UPDATEs on camera), and spine1 sent nothing at all.
  • Packet loss was the same in both (same 9 s timers). The win is blast radius and CPU, not speed.
  • That blast-radius difference is why RFC 7938 fabrics, and today's AI fabrics, run eBGP inside, not just at the border.
  • Link-state still wins in small networks and where the full map is the point (fast-reroute, traffic engineering, ISP cores under BGP).

OpenAI turned BGP off

The switches don't route.
The host does.

In Episode 2, eBGP beat OSPF inside an AI fabric because each flap touched less of the network. OpenAI's MRC goes all the way: no routing protocol in the switches at all. The host writes the whole path into one IPv6 address. When a path dies, the host stops using it and no switch even notices.

Today we build that with the same 5 switches and the same 9 cables as Episodes 1 and 2, and then we break it.

1The idea in plain English

MRC (Multipath Reliable Connection)

A transport from OpenAI with AMD, Broadcom, Intel, Microsoft and NVIDIA, published through OCP in May 2026. The GPU's network card sprays one transfer across hundreds of paths, watches each path, and stops using a bad one within tens of microseconds. It's used in production on 50K to 75K GPU clusters.

SRv6 uSID

Segment Routing over IPv6, in its compressed "micro-SID" form. Every switch owns a short 16-bit ID. A path is just those IDs written in order inside the destination address. Each switch looks at the front, removes its own ID, and forwards on the next one. All it needs is a static table.

Put together: the switches hold a fixed table that never changes. The host chooses the path, so it's the host that has to notice failures. With no protocol there are no neighbors, no hellos, no hold timers, and nothing to converge.

Episode 2's argument was "touch less on every failure." This is the end of that road: a failure touches nothing in the fabric. Only the hosts that were using the dead path change anything.

2The ticket punch: one address, three stops

Think of the address as a train ticket with a row of stops printed on it. At each stop the conductor punches off their own stop and sends you on to the next one printed. Nobody on the train has to know the whole route. They only read the front of the ticket.

Our addressing: the block fcbb:bb00 (32 bits) followed by 16-bit IDs. Spine1 = 100, spine2 = 200, leaf3 = 3, and fe00 = "unwrap and hand it to the host." This is the real address h1 uses to reach h3 through spine1:

h1 writes
fcbb:bb00:100:3:fe00:: "Go to spine1, then leaf3, then unwrap." h1 wraps its IPv4 packet (172.16.1.10 → 172.16.3.10) in IPv6 with this destination.
leaf1
fcbb:bb00:100:3:fe00:: Not leaf1's ticket. It's a plain lookup: static route fcbb:bb00:100::/48 → the spine1 link. No change.
spine1 punches
fcbb:bb00:100:3:fe00:: Matches its own uN SID fcbb:bb00:100::/48. It shifts its 16 bits out and the rest slides left.
on the wire
fcbb:bb00:3:fe00:: The new destination. Static route fcbb:bb00:3::/48 → the leaf3 link.
leaf3 punches
fcbb:bb00:3:fe00:: Matches fcbb:bb00:3:fe00::/64 = End.DX4. It strips the IPv6 wrapper and hands the original IPv4 packet straight out eth2 to h3.

Change one number, change the path. fcbb:bb00:200:3:fe00:: is the same trip through spine2. The host picks which one, packet by packet if it likes. The switches never have to agree on anything.

One address holds up to 6 of these 16-bit stops (F3216 format), so a two-tier fabric path fits easily with no extra header bytes.

3The topology and SID plan

It's the same Clos as Episodes 1 and 2: 2 spines, 3 leaves, 3 hosts, 9 cables. The difference is what's running: zebra + staticd only. bgpd, ospfd, isisd and bfdd are all switched off.

4The entire switch config

This is all of leaf1 (configs/leaf1.conf plus configs/srv6.sh in the kit). Every switch has the same shape. The spines just carry three ipv6 route lines, one to each leaf /48.

interface eth0 ipv6 address fd00:1:100::1/64
Uplink to spine1. Just an address.
interface eth1 ipv6 address fd00:1:200::1/64
Uplink to spine2, which is link 2.
interface eth2 ip address 172.16.1.1/24 ipv6 address fd00:a:1::1/64
Host port. h1 keeps its old IPv4 address.
ipv6 route fcbb:bb00:100::/48 fd00:1:100::2 ipv6 route fcbb:bb00:200::/48 fd00:1:200::2
Two static routes. "Anything for spine1's ID goes up eth0, spine2's up eth1." These never change.
# kernel, via srv6.sh ip -6 route replace fcbb:bb00:1::/48 \ encap seg6local action End \ flavors next-csid lblen 32 nflen 16 dev sr0
My own ticket punch (uN). Block length 32, node ID 16: shift my 16 bits out, then forward on what's left.
ip -6 route replace fcbb:bb00:1:fe00::/64 \ encap seg6local action End.DX4 \ nh4 172.16.1.10 dev eth2
Last stop. Strip the IPv6 wrapper and hand the IPv4 packet to h1.

That's the whole control plane. No router bgp, no router ospf, no neighbors, no hellos, nothing listening on TCP 179.

5What the host does

Each host's main route to a remote leaf lists both paths, and Linux sprays new flows across them:

h1, set up by configs/path-agent.shh1# ip route replace 172.16.3.0/24 \
  nexthop encap seg6 mode encap segs fcbb:bb00:100:3:fe00:: dev eth0 \
  nexthop encap seg6 mode encap segs fcbb:bb00:200:3:fe00:: dev eth0

Then a small bash path agent (configs/path-agent.sh in the kit, about 45 lines) does MRC's job, but slowly:

  • For each remote leaf and each plane, it pings 100 times a second down that exact path (separate routing tables pin each probe to one spine, and the reply comes back on the same plane).
  • After 3 misses in a row (~30 ms) it marks that plane down for that leaf and rewrites the route to use only the other spine. It logs the time to the millisecond.
  • After 50 good replies in a row (0.5 s) it puts both paths back.
  • It runs on every host, because the return path is the far host's choice.

6Run it yourself: the episode in five commands

Download the lab kit (.zip)

Needs Linux with Docker, containerlab and python3, and a kernel with SRv6 uSID support (6.3 or newer; stock Ubuntu 24.04 works, WSL2 may not). All 8 containers use under 300 MB of RAM. Images: quay.io/frrouting/frr:10.5.5 and nicolaka/netshoot.

$ unzip srv6-no-routing-lab.zip && cd srv6-no-routing-lab
$ sudo ./lab.sh up      # 5 switches + 3 hosts, wait until they forward, run every check (~15 s)
$ sudo ./lab.sh check   # no routing daemons / nothing on TCP 179, SID tables, both planes, spray
$ sudo ./lab.sh fail    # break link 2 for 10 s: host agent OFF, then ON; prints lost pings + ms
$ sudo ./lab.sh xray    # capture h1 -> h3 on both planes: the path is written in the packet
$ sudo ./lab.sh down    # destroy the lab

Tested end to end on Ubuntu 24.04 with containerlab 0.73, from the shipped zip: up in 10 s with every check passing, agent ON 5 lost / 69 ms, agent OFF 997 lost (the whole 10 s break), x-ray showing spine1 punch its 100. The README has every detail.

8Exercises (with answers)

1. Add a third stop

Make h1 → h3 traffic go through leaf1's own uN on purpose, then spine1, then leaf3. What's the address, and what does leaf1 do with it?

Answer

fcbb:bb00:1:100:3:fe00::. leaf1 matches its own uN fcbb:bb00:1::/48 and punches 1 off, leaving fcbb:bb00:100:3:fe00::. It then forwards that to spine1 on the static route. That's three stops in one address and still one segment. F3216 fits 6 stops per address. (Tested: 0% loss.)

2. Who notices a dead spine1–leaf3 link?

With all agents running, suspend spine1 eth2. Which hosts move traffic, and which do nothing?

Answer

h1 and h2 move, because their leaf3-via-plane-1 probes fail. h3 moves too, because its replies to h1 and h2 on plane 1 go back through spine1 → leaf3, so its plane-1 probes fail. h1 ↔ h2 traffic via spine1 is untouched, and nothing in the fabric changes. In ep2, a BGP withdraw would have reached every router.

3. Drop the header

Change one of h1's table-1 routes from mode encap to mode encap.red and capture again. What disappears, and why does it still work?

Answer

The Segment Routing Header disappears, leaving just IPv6 with IPv4 inside. It still works because with uSID the whole path already lives in the destination address. You only need the SRH when the path is too long for one 128-bit address. That's why MRC uses uSID: zero extra header bytes. (Tested.)

Each answer has a script in the kit that reproduces it and then undoes it: sudo ./solutions/exercise1/run.sh, exercise2/run.sh, exercise3/run.sh (each folder also has answer.txt).

9What we can't reproduce

Same idea, 1000× slower clock

Real MRCOur lab
RDMA NICs (RoCEv2 extended), path logic in the NIC hardwareNo RDMA NICs. Linux kernel seg6 encap plus a bash loop on each host.
Per-packet spray across hundreds of pathsPer-flow ECMP hashing across 2 paths. One flow stays on one spine.
Packet trimming on congestion (the switch cuts the payload and forwards the header) instead of PFCNo trimming, no congestion signal at all.
Per-path congestion controlNone. It only reacts to "path dead."
Hardware in the NIC reacts in microsecondsA bash agent detects in ~30 ms (100 Hz pings, 3 misses); the outage end to end is ~50–70 ms
50K–75K GPUs, multi-plane fabrics3 hosts, 2 planes, in containers (GNS3 on camera, containerlab in the kit)

What is real: the switches really run no routing protocol, the path really is written into the address by the host, the uSID shift really happens in the Linux kernel, and the outage numbers are measured, not simulated.

Static routes ARE routing. Graham's point on camera: "no routing protocol" doesn't mean no routing. Every switch still has a forwarding table (a few static /48s and its own SIDs); it just never changes. The decisions (which path, when to give up on one) moved out of the switches and into the host. The path agent is the routing now; it just runs at the edge.

The trade-off MRC accepts: a static fabric can't heal itself (agent OFF = loss until someone repairs the link). Every host has to carry that job.
